# Understudy architecture

Understudies are persistent AI coworkers for non-technical teams. Each understudy has its own isolated computer (a container with Chromium), runs on the subscription its owner logged into (Claude Code or Codex CLI), learns a task by watching its owner do it once, and repeats it, asking for approval before irreversible steps.

## Pieces

| Piece | Where it runs | Folder |
|---|---|---|
| Web panel + API + WebSocket hub + gatekeeper MCP + scheduler | Kubernetes, behind `UNDERSTUDY_PUBLIC_URL` | `apps/web` |
| Host supervisor: creates/stops one container per understudy | A VM in an isolated network | `apps/host` |
| Computer: Chromium, screencast, recorder, brain runner | One container per understudy, on the host | `apps/computer` |
| Shared wire types | everywhere | `packages/protocol` |
| Infra scripts and manifests | AWS + Kubernetes | `infra` |

## Direction of connections

Nothing ever connects into the isolated network. The host and every computer dial out to the panel over WSS:

- host → `wss://<panel>/api/ws/host` with `Authorization: Bearer $UNDERSTUDY_HOST_TOKEN`
- computer → `wss://<panel>/api/ws/computer?agent=<id>` with `Authorization: Bearer <computer token>`
- browser → `wss://<panel>/api/ws/viewer?agent=<id>` with the user's session cookie
- computer brain → `https://<panel>/api/mcp` (streamable HTTP MCP) with the computer token

Message shapes live in `packages/protocol/src/index.ts`. Changing them is a contract change between apps; keep it backwards compatible or update all three apps in the same PR.

## Lifecycle

1. A user creates an understudy in the panel. The panel stores it, mints a random computer token (only its hash is stored), and sends `computer_ensure` to a connected host.
2. The host runs the computer image with `AGENT_ID`, `AGENT_TOKEN`, `UNDERSTUDY_SERVER_URL` and a named volume for `/home/agent` (browser profile, CLI logins, recordings). It reports `computer_status`.
3. The computer connects, sends `hello` with which brains are logged in, then streams `frame`s (CDP screencast or the desktop, JPEG) while a viewer is watching. The panel confirms each frame it receives with `frame_ack`, and the server keeps at most two unconfirmed frames per viewer (and none while that socket still has 256 KB waiting), skipping the rest and sending the latest one when the viewer catches up. A slow connection gets fewer frames, and chat, state and approvals never queue behind them.
4. Login: the panel sends `login_start`; the computer runs the official CLI login flow and replies `login_prompt` with the URL/code to show the user; the user may paste a code back with `login_code`; the computer replies `login_done`. Credentials never leave the computer volume.
5. Teaching: `record_start` → the user drives the browser through the viewer (`input` events) and narrates (`record_narration`) → the computer captures DOM-level events and network requests as `recorded` → `record_stop` → the brain turns the log into a `Recipe` and replies `recipe`.
   Teaching from the owner's own browser: the extension (`apps/extension`) pairs with the panel through a one-time code shown in the panel (it never sees the password) and gets a token whose hash is stored. While recording it runs the same capture script and the same secret masking as the computer (`packages/protocol/src/capture.ts`) in the owner's tabs, records the voice with `MediaRecorder` in an offscreen document, and posts events and audio clips to `/api/extension/*`. On stop the panel transcribes the clips, places each transcript segment at its clip's start time plus the segment offset, deletes the audio, merges narration and steps into one timeline and sends it to the computer as `teach_recording`; the brain writes the recipe as in the remote mode.
6. Running: `run_recipe` → the brain executes in the browser (Playwright MCP over CDP to the local Chromium) and asks before every `ask` step, item by item, whatever the page's button is called: `browser_ask_first` (a tool the browser guard adds) for a step done in the browser, the gatekeeper's `request_approval` with the call as `action` for a gatekeeper tool. The panel shows the request and notifies the owner; the answer comes back as the tool result. An approved `browser_ask_first` lets that run's committing browser actions through for five minutes, until the next item is asked, so one item is asked once. The computer also enforces approvals on its own, not on the brain's goodwill: outside an approved item the browser guard pauses submits, pay/send/delete/remove-like clicks, a confirm in a page dialog, and any non-GET request a page script sends while it runs (`browser_evaluate` and `browser_run_code_unsafe`), and the desktop tools refuse to click or type into a web page, so every path into a page meets the same approval and owner rules (the shell is out of scope by choice). With `UNDERSTUDY_RUN_MODEL` set, the run starts on that faster model and the main model takes over the same session only if it stops unfinished.

## Approval modes

Each understudy has an approval policy (`agents.approval_policy`) that its owner sets under Settings › Approvals. It decides what happens to an action that would ask; actions that do not ask (an Allow connector action, a read) are unaffected, and Never actions stay off.

| Mode | What asks |
|---|---|
| `always` | Every committing browser action, every page-script request and every Ask action; the always-allow list and approvals earlier in the conversation cover nothing. Task runs never graduate from their first runs. |
| `on-miss` (default) | Committing browser actions and Ask actions, except on the sites and gatekeeper tools in the always-allow list. A listed site still asks before buying, paying, deleting or removing, changing permissions or roles, and creating an account. |
| `auto` | Like `on-miss`, but before asking the owner a small model reviews the request (see below). |
| `off` | Nothing in the owner's own chat and trusted runs: the browser guard lets actions through, gatekeeper Ask actions run, and `request_approval` from the owner's chat answers approved at once. A task's first runs stop asking. |

- **Always-allow list**: hosts (they cover their subdomains; a public suffix, a shared hosting domain such as `github.io`, a single-label name or an IP address is never accepted) and gatekeeper tool names. A browser approval offers "Always allow on <host>", a gatekeeper tool approval "Always allow <tool>". The host must be the one in the request's `Page` or `Request` field, and it is offered only in the modes that use the list. Only the owner's answer adds the entry; the panel pushes `set_approval_policy` (mode, hosts, owner id) to the computer on connect and on every change. Connector actions keep their own "always allow", which stores Allow for that action.
- **Requests a page script sends**: in `on-miss` and `auto`, one approval covers that host until the end of the conversation (the chat session of the day, the room, the person, or the follow-up wake) or the task run, kept in `~/.understudy/approved-sites.json`; the always-allow list covers it for good. A request whose path looks like signing in, a code or token, a password, a payment or order, a delete, a transfer, an invite, a share, publishing, a comment or sending is not covered by that conversation approval nor by the always-allow list, and asks every time; only `off` lets it through. Usage logs are still dropped without asking, and in a task run a request outside the steps is dropped before any of these shortcuts.
- **Limits that hold in every mode**: owner rules block first; while a task is being learned nothing is sent; an admin ceiling, a run handed over by another understudy and a git push keep asking as before. Turns that are not the owner's (another person, a teammate understudy, a room, an outside sender, a follow-up wake), runs started by a webhook, an email, a hand-off, a watch or a follow-up, and any turn the panel does not know (after a restart, until the next turn starts) ask as `always`, ignoring the list. In a task run that still asks (its first runs, an irreversible step, ask-always), the browser guard stays at `on-miss` at least. `request_approval` takes a `runId` only when it is the run of the current turn.
- **Requests only a person answers**: an approval raised by an admin ceiling, a handed-over run, a git push, or a turn that is not the owner's is stored with `needs_answer = true`.
- **Reviewer** (`auto`): the panel sends a model on the Vercel AI Gateway (`server/reviewer.ts`) the owner's recent words in that conversation (or the run's input and task), the task's steps, and the exact action with its fields, which carry the page script when there is one. The computer strips saved secrets from bodies and scripts before they leave it, and nothing from the vault is sent. Everything is quoted as data. The model answers allow or escalate with a reason. Allow stores the approval as approved with `answered_via = 'reviewer'`; escalate raises the normal request with a `Reviewer` field holding the reason. Every decision is an activity line in the chat. Payments, purchases, account creation, cards and passwords never reach the model and always go to the owner, and so do `[ASK FIRST]` steps, requests in turns that are not the owner's, admin ceilings and handed-over runs. A model error or timeout escalates. After 3 escalations in a row in a conversation or task run, the reviewer steps aside and the owner answers every request until it ends. Without a key, `auto` asks the owner like `on-miss`.
- **When nobody answers** (`fallback`): `wait` (the default) keeps the request open until it expires, and a task run waits with it. With `deny`, a request still pending after 30 minutes is denied; with `allow`, it is approved, but only in a task run that is still running, that the owner or a schedule started, when the owner asked it and when it does not need an answer from a person, so requests from other people, chats, webhooks, emails, hand-offs, watches, follow-ups, admin ceilings and git pushes keep waiting. The sweep picks the oldest eligible requests first. The panel's sweep settles it with `answered_via = 'fallback'`, a note to the brain and a line in the chat, and the Slack message says nobody answered.

## Security rules

- Subscription credentials stay on the computer volume. The panel never sees them.
- A key of an understudy's own stays in the panel, encrypted. The computer holds only a token derived from that understudy's id and computer token, which the panel's model proxy (`/api/model`, `apps/web/src/server/model-proxy.ts`) trades for the real key on Messages calls only, through the same private-address guard as connectors. [CONFIGURATION.md](CONFIGURATION.md) has the details.
- Password fields are masked in recordings (`masked: true`, value replaced).
- The gatekeeper only exposes tools the owner enabled for that understudy, and logs every call.
- Slack and connectors are gatekeeper tools too. The `slack_*` tools (list channels, read, join, post, DM, share a file from `~/files/outbox`) use the panel's Slack app and post with the understudy's name and face; each owner picks per understudy whether they ask first (default), post without asking, or are off. Owner rules are checked on every outward call, even without asking, and writes are rate limited per understudy. Connectors are remote MCP servers an admin adds under People; the panel tests one when it is added and lists its actions.
- Every connector action has a permission per understudy: Allow, Ask or Never. The default comes from the server's own annotations: an action marked `readOnlyHint` (and not `destructiveHint`) is Allow, everything else is Ask, and actions marked `destructiveHint` are flagged in the settings and in the approval. Annotations are untrusted hints: every explicit owner choice is stored (`agents.tools.toolPolicy`) and wins over them, and saving the settings records the hints each action had when its default was decided (`agents.tools.toolHints`). If a connector later describes an action as safer than that record (newly read-only, or no longer destructive), the action falls back to Ask and the settings mark it as changed until the owner chooses. An action that appears later starts from its own default. Tool names are matched without regard to case or compatible Unicode forms wherever a permission is computed, and the gatekeeper refuses any name the connector did not list.
- An admin sets a ceiling per connector (`mcp_servers.ask_all` and `mcp_tool_limits`: ask or never per action). The gatekeeper applies the stricter of the owner's choice and the ceiling on every list and every call. Never actions are left out of the brain's tool list, and a direct call to one is refused before it reaches the server.
- Ask creates an approval with the connector, the action, its description and every argument, bound to a hash of exactly those arguments. When the ceiling allows it, the approval carries a grant, and the owner (only the owner) can answer "Approve and always allow" in the panel, on Slack or on Telegram, which stores Allow for that one action.
- Every connector call is stored in `tool_calls` with its verdict (allowed, approved, denied, blocked) and, when a task run is in progress, its run id, and the run page lists them.
- The isolated network has no route to production networks; egress is internet only.
- Everything specific to one deployment (domain, allowed email domain, Slack workspace) is configuration, never code.

## Learning without being taught

An understudy also offers to keep work it was not taught. Two signals start it:

- **Repetition.** When the owner writes in the panel or on Slack, the panel compares the message with that owner's other messages to the same understudy from the last 30 days (words without stopwords, numbers or links; Jaccard similarity of at least 0.5; asks less than an hour apart count once). On the third similar ask, unless an existing task or a recent suggestion already covers it, the chat message reaches the computer with `repeated: { times, since }`.
- **A long ad-hoc job.** The computer counts the actions in each chat turn (reads, screenshots and approvals do not count).

After a successful chat turn with either signal, and when the brain did not already call `save_task` or `propose_task`, the computer runs one quiet follow-up in the same session asking the brain to call the gatekeeper tool `propose_task` if the work is a routine. Nothing it writes in that follow-up reaches the chat.

`propose_task` takes a draft (title, why, steps with `ask_first`, inputs, an optional cron) and stores it in `task_proposals` after the usual recipe normalization, so commit-like steps ask first. It refuses a routine that is already a task or that the owner dismissed in the last 30 days, updates a waiting suggestion for the same routine instead of adding another, and keeps at most three waiting. The chat shows it as a card and, when Slack is on, it goes to the active Slack thread or as a direct message to the owner with Save task and Not now buttons. Only the owner can answer. Saving creates the task with the suggested schedule turned on (the first runs still ask before every step); "Save and edit" creates it paused and opens the editor. Nothing is saved without that choice.

## Follow-ups

An understudy can book its own next look at something with the gatekeeper tools `schedule_followup` (when, note, optional task, optional progress), `list_followups` and `cancel_followup`. There is no separate scheduler: rows in `followups` are fired by the same panel scheduler that runs task schedules, on its 30-second sync.

- **When**: a delay ("2h", "1h 30m", "3d") or a time, read in `UNDERSTUDY_TIMEZONE` unless it carries an offset. At least 10 minutes and at most 60 days ahead, and at most 20 waiting per understudy; the count and the insert happen under a per-understudy lock.
- **Where it wakes**: in the conversation it was booked from (a trusted channel thread keeps its origin), or as a normal run of a task (`trigger: "followup"`) when it was booked during that task's run or names one. A paused task wakes the chat instead. The wake runs as the owner's understudy with the usual rules and connector permissions; a follow-up run always asks before every [ASK FIRST] step, and the note reaches the brain quoted as untrusted data that approves nothing, never as the owner's words.
- **Chains**: a follow-up booked while handling a wake continues that wake's chain. The computer reports the wake in its `turn` message (`followup`), and the run a turn belongs to (`runId`), so a booking from the chat is never attached to a task run that happens to be running. Rebooking without `progress` counts as an empty wake; at the third in a row the booking is refused, the chain's waiting follow-ups stop and the owner is told. Whatever `progress` says, a chain stops after `UNDERSTUDY_FOLLOWUP_MAX_CHAIN_WAKES` wakes and an understudy wakes for follow-ups at most `UNDERSTUDY_FOLLOWUP_MAX_DAILY_WAKES` times in 24 hours; past that, bookings are refused, due follow-ups stop and the owner is told.
- **Who may book**: never a turn answering someone other than the owner, a turn started by a teammate, a room or an outside sender (the computer marks it `untrusted` in its `turn` message), or a webhook, email, handoff or watch run; the restricted gatekeeper address does not serve these tools either.
- **Panel**: upcoming follow-ups appear on the agent card, in the Tasks tab, in Today and in the run history, where the owner can cancel them. Booking and waking each leave a line in the chat.

## Always on

Understudies do not depend on their owner being online. The computer runs 24/7 on the host; the panel's scheduler and triggers start runs; approvals wait in the panel (and optionally Slack) until answered, and the run resumes from the approval.

- **A run waits for its owner.** An approval stays valid for 24 hours, but one tool call waits at most 30 minutes and then answers `pending`. A pending answer is never an end: asking again for the same item in the same run (`request_approval`, a connector or Slack call, `call_api`, `browser_ask_first` or the same browser action) joins the open request instead of asking twice, and the browser guard and the vault remember their open requests per run in `~/.understudy/approval-asks.json`. Nothing that asked runs on its own after its call was cut off: every wait ends after one round (or as soon as the client cancels the call, even when the cancellation arrives in a separate request), a connector, Slack or git call goes through only inside a live call, and it claims the owner's yes once, so the same call repeated later in the run goes through without asking again, and a call the owner refused in this run is refused again without asking. Outside a run, a pending answer tells the brain to say it waits for the owner and end its turn. Checks that belong to "this run" (earlier refusals, the run a call is logged on, which approval a call may use) follow the run of the turn the computer reported, not the newest open run, so runs of different tasks of the same understudy that are open at the same time stay apart. If the brain's turn ends while the run has an approval pending, the computer keeps the run open, waits through the gatekeeper's `run_approvals` tool until the owner answers or the request expires (it keeps trying while the panel cannot be reached), and resumes the same brain session with the answers. The computer keeps its open runs in `~/.understudy/open-runs.json`: after a restart it picks up a run that waits for its owner and resumes it, and closes any other run it was in the middle of with a summary that says so. The run page shows a waiting run (with the answer button only for people who can answer), the Stop button stays available while the understudy waits, and the owner gets one Slack reminder after an hour. A scheduled run does not start while an earlier run of the same task is still open; the chat notes that it was skipped.
- **A run that goes silent is closed.** Every 30 seconds the panel looks at running runs. A run that has started is closed as failed when its computer has sent nothing for it (no activity or message line of that run) for 35 minutes and none of the run's own approvals is pending (a request with no expiry counts for a day at most). A run its computer never started is closed after 35 minutes only when that understudy's computer has shown nothing at all and nothing of that understudy waits for its owner, so a run queued behind other work stays; a run still queued for a computer that is off is left to the delivery queue. The summary says when the computer went quiet and what it was doing, and names an answer that came after that; the owner gets the usual failure notice (not for runs whose last sign of life is more than a day old). The computer gets `run_stop`, which cancels that run's turn, and gets it again whenever it still acts for that run (at most once a minute) and when it reconnects: a closed run's approvals are refused, `run_approvals` reports it as closed, and a late `run_finished` changes nothing.

## Memory without blowing the context

No conversation grows forever. Every run is a fresh brain session that starts from a small, fixed briefing and reads more only on demand.

- `~/memory/profile.md`: who the understudy is, its owner, its role, its rules. Short, edited by the owner and by the understudy itself.
- `~/memory/recipes/<id>.md`: one file per learned task, the compact recipe.
- `~/memory/journal/YYYY-MM-DD.md`: one line per run outcome, written at the end of every run.
- `~/memory/notes/*.md`: facts the understudy decided to keep (`remember` writes here; `recall` searches here).
- `~/runs/<runId>/`: full transcript, screenshots and recorded events of that run. Never loaded into a new session; only searched when needed.

A run's briefing is: profile + the recipe being run + the last 7 journal lines + the task input. Chat with the owner uses one rolling session per day; when it ends, the brain writes a short summary into the journal and the next day starts fresh. Long recordings are reduced before reaching the brain: consecutive inputs on the same field collapse, network requests keep only method, path and status, and screenshots are sampled. The brain CLIs also compact on their own; the files above are what survives compaction.

## Channels

A channel is another place where people hold a conversation with an understudy, with the same chat, memory, approvals and run history as the panel. Each understudy has at most one connection per kind (`agent_channels`), and each person it talks to there gets a thread (`channel_threads`: the peer, whether it is the owner, and what the channel needs to answer in place).

- **Inbound**: the channel's endpoint authenticates the provider, maps the destination to the understudy, classifies the sender (owner, allowed, unknown) and either holds the message for the owner, drops it, or delivers it as a normal `chat`. A message from anyone but the owner carries `external: { channel, sender }`, and the computer briefs the brain with it quoted as data and the rule that it never authorizes anything.
- **Reply route**: the panel sends each channel message with `origin` (its thread), and the computer sends `turn` with that origin when the turn starts. Replies, files shared with `share_file` and approvals follow the turn's origin; turns from the panel or Slack never write to a channel thread. An owner's message also records the thread in `channel_routes` for 30 minutes, once it is dispatched to the computer. A panel message clears it, and a later Slack message wins over it. Replies are buffered on the thread and sent when the turn ends (state back to calm, waiting or stuck), or after 90 seconds at the latest. Messages from anyone but the owner run in a separate session with no built-in tools whose only MCP server is the restricted gatekeeper address (`/api/mcp/restricted`). It serves only `request_approval`, `wait_for_approval` and `notify_owner`, labels them with who the understudy was answering and rate limits them, whatever the panel remembers about the turn; the regular address also refuses other tools while such a turn is current.
- **Approvals**: while the route is active, a new approval also reaches the owner on that channel through the adapter's `sendApproval`.
- **Slack for people other than the owner**: a team understudy also answers its team on Slack, and anyone with an account when its owner allows it. Each of those conversations is a `slack_asker_threads` row sent as the message's `origin`, and the panel routes a turn's replies there only when the row belongs to the person the turn ledger expected. Approvals raised for someone outside the team go to the owner and approvers by direct message. [CHANNELS.md](CHANNELS.md) has the rules.
- **Adapters**: every reply goes through `currentConversation` and `relayReply` in `apps/web/src/server/channels/relay.ts`, which pick the conversation that spoke last and hand the reply to its adapter. Buffered adapters implement `send` and optionally `sendApproval` (Telegram: a bot per understudy, webhook or polling, approvals as buttons; WhatsApp: the owner's own account linked as a device with Baileys, sessions held by the panel process, approvals answered with 1 or 2). Live adapters implement `live` (Slack: replies, streaming, status, approvals in the thread, panel mirror and task progress). [CHANNELS.md](CHANNELS.md) has the contract and the designs for Teams, WhatsApp and SMS.

## Rooms

A room is a group chat between an owner and two or more of their own understudies (`rooms`, `room_participants`, `room_messages`). Only the owner reads it or writes in it, over `wss://<panel>/api/ws/room?room=<id>`.

- The owner's message wakes every participant, or only the ones named with `@Name`. Each wake is a `room_turn` to the computer: a fresh brain session whose prompt says it is a group room, who is in it, how to address someone, the recent transcript as quoted data, and that teammates never authorize irreversible steps.
- The computer tags what that turn says, streams and does with the `roomId`, so it lands in the room and not in the private chat, drops a reply that is only `PASS`, and ends with `room_turn_done`.
- An understudy's message wakes only the teammates it names, one level deeper. There is no limit by default: they go on as long as they keep naming each other. A teammate named while it is still working gets one more turn after it finishes instead of a parallel one. A turn that does not finish in 15 minutes is closed.
- The owner's Stop button ends every running turn in the room at once, drops the turns still waiting for a computer, and posts a note; nobody answers until the owner writes again.

## Conversations between understudies

Outside rooms, an understudy reaches a teammate (another understudy of its owner or, when it is on a team, any understudy on that team, whoever owns it) with `message_agent` (a chat turn marked as coming from a teammate) or `hand_off` (starts one of the teammate's tasks; every step still needs its own owner's approval). Each one is kept in `agent_messages`, and the panel's Conversations page shows every pair as a thread next to the owner's rooms.

- No depth or hourly limit applies by default. `UNDERSTUDY_AGENT_TALK_CEILING`, when set, is the most turns in a row understudies may take among themselves, in rooms and between pairs.
- Stop on a pair thread records a `stop` line in `agent_messages`, drops their queued messages to each other, and refuses `message_agent` and `hand_off` between the two until the owner lets them talk again (a `resume` line).
- A teammate's word never approves an irreversible step; that stays with each understudy's own owner.
- A message or hand-off between understudies of different owners says whose understudy sent it, and the one receiving it is told that what it answers reaches that person. Either owner can stop the pair.
- A turn answering a Slack guest (someone who cannot chat with the understudy in the panel) only reaches its owner's own understudies, never the rest of the team.

## Files in the chat

The owner attaches files in the chat (paperclip, drag and drop, paste). The browser streams each one in 8 MB chunks to `/api/files/<agent>/uploads` on the panel, which passes every chunk to the computer over its socket (`upload_open`, `upload_chunk`, `upload_finish`) and answers only after the computer wrote it, so nothing is staged on the panel. A failed chunk is retried from the byte count the computer reports; the computer refuses an upload that does not fit on its disk before any byte moves. The limit is `UNDERSTUDY_UPLOAD_MAX_BYTES` (4 GB by default). Finished files land in `~/files/inbox` under a sanitized, unique name, and the message the brain receives lists each one with its full path, type and size.

The brain sends files back with the gatekeeper tool `share_file`: the computer copies the file into `~/files/outbox` when it lives elsewhere in the home folder (never from hidden folders) and the panel posts it in the chat. Every file in a message renders as a card with a preview. Downloads and previews stream from `/api/files/<agent>/raw` with byte ranges (`file_read`), and PDF first pages and video posters come from `/thumb`.

Only the owner uploads. The owner can read anything in the inbox and outbox; approvers and viewers can read only files that were posted in that understudy's chat. Files are served with `nosniff`, a sandboxing Content-Security-Policy, and as downloads unless they are images, video, audio or PDF; HTML and SVG are never rendered.

## Rich replies on Slack

Chat replies reach Slack as one `markdown` block, except when the reply is structured. The panel then turns the same markdown into Block Kit (`server/slack-blocks.ts`): `#`/`##` headings become `header` blocks, two or more `**Label:** value` lines become `section` fields, the first pipe table becomes a native `table` block, a rule becomes a `divider`, a trailing italic or `Source:` line becomes `context`, and trailing links become URL buttons. Everything else stays `markdown`. A ```` ```chart ```` fence holding `{"type":"bar"|"line","title","labels","series":[{"name","values"}],"unit"}` (at most 24 labels and 4 series) is drawn by `lib/chart.ts`: the chat renders it as inline SVG, and Slack gets an `image` block pointing at `/api/charts/<payload>.<sig>.png`, where the payload is the normalized chart and the signature an HMAC with the server secret. The route renders the PNG with resvg and a bundled Inter font, caches it in memory and serves it as immutable; there is no image without a public `UNDERSTUDY_PUBLIC_URL`, and the chart's numbers are always in the notification text. A message that would break Slack's limits (50 blocks, 12,000 markdown characters, one table of at most 100 rows, 20 columns and 10,000 characters) keeps the plain markdown block, and if Slack still refuses the blocks the reply is posted again as plain markdown. Streamed replies are swapped for the rich blocks with `chat.update` once they finish.

## Artifacts

An artifact is something the understudy made for people to look at (a deck, a document, a page, a chart, a small app, a PDF, an image), with a title and a list of immutable versions. The brain publishes one with the gatekeeper tool `publish_artifact` (path, title, optional `artifact_id` to add a version, optional note). The panel takes a snapshot on the spot: it reads the file over the computer socket (`file_share`, `file_read`), and for PDF and office files asks the computer to render page images (`artifact_render`, `artifact_page`; LibreOffice converts, poppler rasterizes, up to 60 pages). Metadata lives in Postgres (`artifacts`, `artifact_versions`, `artifact_links`); bytes and pages go to an S3-compatible bucket under a key per version id, or to `artifact_blobs` in Postgres when no bucket is set. Each version keeps its own kind, and an understudy's artifacts are capped in total (`UNDERSTUDY_ARTIFACT_AGENT_MAX_BYTES`). A version opens even while the computer sleeps.

The card lands in the chat and opens beside it in the Artifacts tab: versions, zoom, pages, full screen, download. "Request edits" sends a normal chat message with a structured reference (artifact, version, the selected text or the page). The panel first writes that exact version back into `~/files/inbox/artifacts/<id>/v<n>/` with `file_put`, and the computer briefs the brain with the path, the quote marked as data, and the instruction to publish again with the same `artifact_id`.

Rendered content never runs with the panel's origin:

- HTML loads in an iframe with `sandbox="allow-scripts"` (no `allow-same-origin`, popups, forms or top navigation), and the response itself carries `Content-Security-Policy: sandbox allow-scripts` so it stays sandboxed when opened directly. The same policy closes the network: `connect-src`, `form-action`, `frame-src`, `worker-src` are `'none'`, images and media only `data:`/`blob:`, scripts and styles inline or from cdnjs, jsdelivr and unpkg, fonts also from Google Fonts. `frame-ancestors` is the panel only, and the panel sends `frame-src <content origin>/api/artifacts/c/`, so an artifact that tries to navigate its frame elsewhere (to leak its content or show a fake sign-in) is blocked.
- Content URLs carry a signed token (HMAC, one version, one hour) instead of the session cookie, so the content route works the same on a separate origin (`UNDERSTUDY_ARTIFACT_ORIGIN`).
- The panel prepends a short script to HTML that only reports the selected text and blocked requests with `postMessage`. The panel accepts messages only from that iframe's window, checks their shape and size, and treats them as data. The quote reaches the brain as a JSON string on one line, so a crafted selection cannot close it and pose as the owner.
- The content route is rate limited per client and version and sends an `ETag` with `immutable` caching, since a version never changes.
- Markdown renders with the chat's own renderer (no raw HTML, no remote images); PDF and office files are page images; SVG only as an image with a script-free policy; downloads are `application/octet-stream` attachments.
- What is left: an interactive artifact can still leak its own content through channels a CSP does not close (WebRTC, DNS prefetch, a CDN script URL). It cannot read anything outside itself.

The owner can create a public link for the version on screen (`/shared/<token>`): the token is random, only its hash is stored, it expires after 30 days and every link can be turned off. The link always shows that version, never a later one, so an injected agent cannot push new content through a link someone already has. The page has no panel controls, hides the artifact id, uses content tokens that last ten minutes, and stays sandboxed.
